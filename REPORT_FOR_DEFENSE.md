# EcoPet Planner
## Подробный отчёт о разработке и материал для защиты проекта

**Тип проекта:** клиент-серверное веб-приложение  
**Предметная область:** создание цифрового мемориала питомца в виде посадки дерева и ведение дневника ухода  
**Архитектура:** одностраничный frontend (SPA) и REST API  
**Backend:** Python, Django, Django REST Framework  
**Frontend:** JavaScript, React, Vite  
**Основная СУБД:** PostgreSQL  
**Картографическая библиотека:** Leaflet / React-Leaflet  
**Документ:** описание реализованного состояния проекта для демонстрации и защиты

> Этот отчёт описывает фактический код проекта и проведённые проверки. Расчёт биодеградации является демонстрационной экспертной моделью с заданными коэффициентами, а не лабораторно подтверждённым прогнозом.

---

## 1. Краткая аннотация

EcoPet Planner помогает владельцу питомца оформить память о нём в форме живого мемориала. Пользователь указывает сведения о питомце и параметры предполагаемого места посадки. Система сохраняет анкету и расчёт, вычисляет ориентировочный срок разложения био-капсулы, рекомендует дерево из каталога, позволяет выбрать эко-парк или завершить создание посадки на собственном участке. После этого пользователь может вести дневник ухода и скачать PDF-паспорт.

В ходе разработки была устранена ключевая причина отсутствия рекомендаций деревьев: в рабочей PostgreSQL-базе каталог был пуст. Добавлена миграция с начальными данными десяти пород и обновлён подбор дерева по климату, почве и предпочтениям пользователя.

Основные результаты:

- реализованы API пользователей, профиля, питомцев, расчётов, эко-зон, посадок и журнала ухода;
- разделены главная страница с дневником и отдельный личный кабинет;
- добавлены фотография питомца и подробный PDF-паспорт с поддержкой кириллицы;
- реализована интерактивная карта активных эко-зон;
- поддержан сценарий посадки на собственном участке без привязки к эко-парку;
- реализована согласованная формула прогноза биодеградации;
- возраст питомца вычисляется автоматически по датам рождения и ухода;
- добавлены и запущены проверки основных backend-сценариев.

## 2. Цель, задачи и результат

### 2.1. Цель

Разработать веб-приложение, которое объединяет анкету питомца, сохранение параметров мемориала, рекомендацию дерева, выбор места посадки и последующий дневник ухода в одном пользовательском сценарии.

### 2.2. Задачи разработки

1. Организовать frontend и backend как отдельные, взаимодействующие части системы.
2. Использовать PostgreSQL для постоянного хранения пользователей и доменных данных.
3. Реализовать регистрацию, авторизацию и доступ пользователя только к принадлежащим ему данным.
4. Создать структуру хранения питомцев, расчётов, пород деревьев, эко-зон, посадок и записей ухода.
5. Сохранять исходные параметры расчёта, чтобы формировать из них документ и показывать результат повторно.
6. Добавить вычислимый прогноз срока биодеградации и подбор подходящей породы.
7. Предусмотреть два варианта посадки: в эко-парке и на собственном участке.
8. Создать доступный интерфейс для загрузки фотографий, ведения дневника и изменения личных данных.
9. Проверить основные пользовательские сценарии автоматизированными backend-тестами и frontend production-сборкой.

### 2.3. Полученный результат

Приложение представляет собой работающий прототип с реальным REST API и PostgreSQL. В проекте реализованы не только статические экраны, но и сохранение данных, JWT-аутентификация, связи между сущностями, файловая загрузка, генерация PDF и миграции базы.

## 3. Архитектура и взаимодействие компонентов

### 3.1. Общая схема

```text
Браузер
  └─ React SPA
       ├─ формы и экраны приложения
       ├─ Leaflet / OpenStreetMap
       └─ API-клиент (JSON, multipart/form-data, JWT, PDF blob)
              │ HTTP / REST
              ▼
       Django REST Framework
         ├─ аутентификация и разрешения
         ├─ сериализаторы и валидация
         ├─ бизнес-логика расчётов
         ├─ генерация PDF
         └─ ORM
              │ SQL
              ▼
           PostgreSQL
```

Frontend отвечает за ввод и отображение данных. Backend выполняет проверку входных значений, контролирует владение объектами, применяет бизнес-правила и сохраняет данные. PostgreSQL обеспечивает долговременное хранение. Фотографии сохраняются в файловом хранилище Django `MEDIA_ROOT`, а в БД хранится путь к файлу.

Ключевые настройки backend находятся в [backend/petMemorial/settings.py](backend/petMemorial/settings.py), маршруты — в [backend/petMemorial/urls.py](backend/petMemorial/urls.py). Клиентская маршрутизация по экранам сделана внутри SPA в [frontend/src/App.jsx](frontend/src/App.jsx), поэтому для переходов между главной страницей, калькулятором, картой и профилем не требуется отдельная серверная HTML-страница.

### 3.2. Почему выбрана такая архитектура

- **React SPA:** позволяет менять экраны и состояние после ответов API без полной перезагрузки страницы. Это подходит для последовательной формы расчёта и интерактивной карты.
- **REST API:** отделяет интерфейс от правил хранения и обработки. Backend можно тестировать независимо от браузера; API также может использоваться другим клиентом.
- **Django REST Framework:** предоставляет согласованные механизмы сериализации, валидации, разрешений и типовых CRUD-endpoint'ов. Для коллекций и деталей используются generic views, а для специфичного расчёта и PDF — APIView.
- **PostgreSQL:** выбрана одна целевая СУБД с транзакционными и реляционными возможностями. По требованию проекта SQLite не используется как запасной режим, поэтому локальный запуск требует работающего PostgreSQL.
- **JWT:** позволяет SPA передавать токен с запросами к защищённым endpoint'ам, не полагаясь на серверную сессию в браузере.
- **Leaflet:** даёт интерактивное перемещение, масштабирование, fit-to-markers и маркеры, что нельзя получить от статической иллюстрации карты.
- **ReportLab:** создаёт PDF на сервере из сохранённого расчёта; таким образом документ соответствует данным из БД, а не только текущему состоянию формы браузера.

## 4. Backend: реализованные компоненты и обоснование

### 4.1. Настройки и PostgreSQL

В [backend/petMemorial/settings.py](backend/petMemorial/settings.py) движок базы указан как `django.db.backends.postgresql`; параметры подключения считываются из окружения. Это исключает незаметное переключение между SQLite и PostgreSQL: приложение должно стартовать с настроенной целевой БД.

Настройки также подключают Django REST Framework, SimpleJWT, CORS и доменные приложения `calculator`, `zones`, `tracker`, `users`. Загруженные фотографии обслуживаются через `MEDIA_URL` и `MEDIA_ROOT` в режиме разработки.

**Обоснование выбора PostgreSQL:** модели приложения имеют связанные сущности, ограничения и миграции. Единая PostgreSQL-конфигурация помогает проверять тот же класс хранилища, который принят для проекта, и не создавать ложное впечатление, что данные синхронизируются между разными БД.

### 4.2. Пользователь и профиль

В [backend/users/models.py](backend/users/models.py) используется пользовательская модель Django с email как логином и дополнительным телефоном. Регистрация выполняется через [backend/users/views.py](backend/users/views.py), поля профиля описаны в [backend/users/serializers.py](backend/users/serializers.py).

`GET/PATCH /api/v1/auth/profile/` работает только с `request.user`: отдельный пользователь не передаёт идентификатор профиля, который можно было бы подменить. Это упрощает контракт endpoint'а и снижает риск случайного изменения чужой записи.

### 4.3. Карточка питомца и вычисление возраста

Модель `Pet` находится в [backend/calculator/models.py](backend/calculator/models.py). В ней хранятся владелец, имя, вид, порода, вес, даты и файл фотографии.

В [backend/calculator/serializers.py](backend/calculator/serializers.py):

- `PetSerializer` определяет поля API;
- фото ограничено 10 МБ;
- пустые строки дат нормализуются в `None`, что важно для multipart-запросов из браузера;
- проверяется, что дата ухода не раньше даты рождения;
- `age_years` сериализуется как производное read-only значение `age_at_death_years`.

Возраст в полных годах вычисляется в свойстве модели: сначала берётся разница календарных лет, затем вычитается один год, если годовщина рождения в году ухода ещё не наступила. Например, при рождении 20 декабря 2018 и дате ухода 19 декабря 2026 возраст равен 7 полным годам.

Ручной возраст из пользовательского интерфейса удалён, так как он мог не соответствовать введённым датам. Историческое поле `age_years` оставлено в таблице для совместимости с ранее сохранёнными данными, но текущий API возвращает вычисленное значение и не использует ручной ввод как источник истины.

### 4.4. Расчёт мемориала и срока биодеградации

Расчёт принимает вес, сценарий, регион, климат, почву, освещённость, близость воды, предпочтения ухода и темпа роста, комментарий и, если пользователь вошёл в аккаунт, ссылку на питомца. Валидация входного запроса находится в `CalculationRequestSerializer`, обработчик и сохранение — в [backend/calculator/views.py](backend/calculator/views.py).

Отдельная функция бизнес-логики вынесена в [backend/calculator/degradation.py](backend/calculator/degradation.py). Это позволяет проверять формулу отдельно от HTTP и БД:

```text
Ttotal = Tbase × Kweight × Ksoil × Kclimate
```

Используемые подтверждённые значения:

| Параметр | Значение | Обоснование в приложении |
|---|---:|---|
| `Tbase` | 6 месяцев | Текущий продуктовый материал — смесь мицелия и прессованного торфа; принято согласованное базовое значение |
| `Kweight` при весе `< 5 кг` | 0.9 | Нижняя весовая группа |
| `Kweight` при весе `5–20 кг` | 1.0 | Базовая весовая группа |
| `Kweight` при весе `> 20 кг` | 1.2 | Повышенная поправка на массу |
| `Ksoil` — чернозём | 0.9 | Коэффициент задан требованиями |
| `Ksoil` — песок / суглинок | 1.0 | Базовый коэффициент; для суглинка значение согласовано отдельно |
| `Ksoil` — глина | 1.3 | Коэффициент задан требованиями |
| `Kclimate` — южный | 0.9 | Согласованная поправка |
| `Kclimate` — умеренный | 1.0 | Базовый климатический коэффициент |
| `Kclimate` — континентальный | 1.1 | Согласованная поправка |
| `Kclimate` — северный | 1.3 | Согласованная поправка |

Пример: при весе 4,5 кг, умеренном климате и суглинке:

```text
Ttotal = 6 × 0.9 × 1.0 × 1.0 = 5.4 месяца
```

Результат сохраняет вес отдельным снимком в `CapsuleCalculation.weight_kg` вместе с числовым сроком в `estimated_degradation_months`. Это важно: если пользователь позднее изменит вес в карточке питомца, старый расчёт и созданный по нему PDF сохранят первоначальный прогноз.

Для неизвестных категорий почвы или климата запрос отклоняется с понятной ошибкой, вместо молчаливого применения случайного коэффициента. В `CalculationSerializer` клиент получает `degradation_breakdown`, содержащий базу, вес и три коэффициента.

Размер капсулы выбирается отдельно от срока: меньше 5 кг — `S`, 5–20 кг включительно — `M`, свыше 20 кг — `L`.

### 4.5. Каталог пород и причина отсутствия деревьев

Модель породы дерева — `TreeSpecies` в [backend/calculator/models.py](backend/calculator/models.py). Публичный список отдаётся через `GET /api/v1/calculator/tree-species/`.

При диагностике в PostgreSQL было установлено, что число записей каталога равно нулю. Endpoint работал, но возвращал пустой массив, поэтому фронтенд показывал состояние «Подходящая порода не найдена». Проблема была не в рендеринге React, а в отсутствии данных для отображения и рекомендации.

В [backend/calculator/migrations/0004_seed_tree_species.py](backend/calculator/migrations/0004_seed_tree_species.py) добавлена миграция с десятью породами:

1. сосна обыкновенная;
2. берёза повислая;
3. ель европейская;
4. рябина обыкновенная;
5. лиственница сибирская;
6. клён остролистный;
7. липа мелколистная;
8. дуб черешчатый;
9. каштан посевной;
10. граб обыкновенный.

Миграция не перезаписывает уже наполненный каталог: если в таблице есть записи, начальные строки не вставляются. Это защищает существующие пользовательские данные от дублирования/перезаписи при обновлении схемы.

Функция `_matching_tree_species` в [backend/calculator/views.py](backend/calculator/views.py) отбирает виды с совпадающим климатом и ранжирует их по совпадению почвы, уровня ухода и желаемого темпа роста. Поэтому каталог требуется не только заполнить, но и наполнить согласованными значениями совместимости.

**Важное уточнение для демонстрации:** в начальных данных заполнены названия и характеристики пород, но фотографии деревьев в миграцию не добавлены. Поле модели `image` остаётся необязательным, а карточка рекомендации использует иллюстративную иконку ростка. Таким образом, «деревья отображаются» как виды/рекомендации; реальные фото пород не входят в текущую поставку.

### 4.6. Эко-зоны, посадки и дневник ухода

Модель `EcoZone` содержит название, тип, адрес, координаты, регион, климатическую зону, признак близости к воде, наличие услуги ухода, правила и признак активности. Поле `is_demo` отдельно указывает, что координата добавлена для демонстрации, а не подтверждает действующее разрешённое место посадки. Публичный API отдаёт активные зоны, а административные endpoint'ы доступны только staff-пользователям.

Модель посадки и записи журнала находятся в [backend/tracker/models.py](backend/tracker/models.py). `PlantedTree` связывает одну запись расчёта, питомца, вид дерева и, если выбран эко-парк, зону. Поле `eco_zone` допускает `NULL`, чтобы посадка на собственном участке не требовала фиктивного эко-парка.

В [backend/tracker/serializers.py](backend/tracker/serializers.py) валидируется владение связанными объектами. Посадка не должна ссылаться на чужой расчёт или питомца, а дневниковая запись — на посадку другого пользователя. Список посадок ограничивается текущим пользователем в [backend/tracker/views.py](backend/tracker/views.py).

Миграция [backend/zones/migrations/0002_seed_eco_zones.py](backend/zones/migrations/0002_seed_eco_zones.py) добавляет исходные четыре точки, а [0003_region_climate_water_and_demo_locations.py](backend/zones/migrations/0003_region_climate_water_and_demo_locations.py) привязывает их к регионам и климатам и добавляет демонстрационные координаты для Истринского водохранилища, Оби и Онежского озера. В итоге представлены Москва, Московская область, Санкт-Петербург, Краснодарский край, Новосибирская область и Карелия, охватывающие четыре модельные климатические категории. Координаты не являются утверждением о доступности земли для посадок; это честно показывается и в интерфейсе карты.

Список регионов для формы калькулятора строится из активных зон. При выборе региона климат назначается автоматически; backend дополнительно проверяет совпадение для известных регионов. Вопрос о близости к воде ограничен вариантами «Да»/«Нет»: при «Да» карта показывает только зоны с `near_water: true`, а при «Нет» — все зоны подходящих региона и климата.

### 4.7. PDF-паспорт

PDF строится обработчиком `DownloadPDFPassportView` в [backend/calculator/views.py](backend/calculator/views.py) по объекту расчёта из БД. В документ включаются:

- данные питомца, даты и вычисленный возраст;
- фотография питомца при наличии доступного файла;
- параметры, указанные в форме;
- выбранный сценарий, регион, климат, почва и предпочтения;
- материал и размер капсулы;
- прогноз срока с раскрытием формулы и коэффициентов;
- рекомендованная порода дерева.

ReportLab используется как библиотека построения PDF, поскольку позволяет генерировать документ непосредственно на backend и управлять таблицами, стилями, страницами и встраиваемыми шрифтами.

Для поддержки кириллицы в проект включён Noto Sans: [backend/assets/fonts/NotoSans.ttf](backend/assets/fonts/NotoSans.ttf); лицензия хранится в [backend/assets/fonts/OFL.txt](backend/assets/fonts/OFL.txt). Встраивание шрифта устраняет проблему квадратов при просмотре PDF на устройствах, где нужный системный шрифт не установлен. Пользовательские строки HTML-экранируются перед передачей в Paragraph, чтобы специальные символы из комментария корректно отображались.

PDF выдаётся как `application/pdf`, а неизвестный ID расчёта возвращает `404`. Frontend скачивает бинарный ответ, а не пытается разобрать его как JSON.

### 4.8. Миграции

Миграции Django описывают схему и начальные данные. Ключевые миграции проекта:

- `0001_initial` и `0002_initial` — исходные модели и связи calculator;
- [0003_capsulecalculation_estimated_degradation_months_and_more.py](backend/calculator/migrations/0003_capsulecalculation_estimated_degradation_months_and_more.py) — снимок веса и числовой прогноз срока;
- [0004_seed_tree_species.py](backend/calculator/migrations/0004_seed_tree_species.py) — начальные данные десяти пород;
- [0002_seed_eco_zones.py](backend/zones/migrations/0002_seed_eco_zones.py) — исходные четыре точки;
- [0003_region_climate_water_and_demo_locations.py](backend/zones/migrations/0003_region_climate_water_and_demo_locations.py) — регионы, климат, близость к воде и демонстрационные точки.

Использование миграций делает изменения схемы и начального набора данных воспроизводимыми на других PostgreSQL-инсталляциях.

## 5. Frontend: реализованные экраны и обоснование

### 5.1. Корневое приложение и навигация

В [frontend/src/App.jsx](frontend/src/App.jsx) хранится состояние текущего экрана, профиль пользователя и последний расчёт мемориала. Навигация разделяет четыре пользовательские области:

- «Мой сад»;
- «Создать мемориал»;
- «Эко-парки»;
- «Личный кабинет».

Выбор сделан в пользу простого состояния React, потому что приложение использует ограниченный набор экранов без сложной иерархии URL. Переходы централизованы в App, поэтому сценарии создания мемориала могут передавать результат калькулятора на экран карты.

### 5.2. Вход и регистрация

Экран реализован в [frontend/src/Auth.jsx](frontend/src/Auth.jsx). Он отправляет регистрацию/логин через общий API-клиент, сохраняет JWT и сообщает App о входе. Поддержка автоматического обновления access-токена и сериализация JSON/`FormData` находятся в [frontend/src/api.js](frontend/src/api.js).

`FormData` не получает вручную заданный `Content-Type`: браузер сам формирует multipart boundary. Это необходимо, чтобы backend корректно прочитал файл фотографии.

### 5.3. Калькулятор

Форма калькулятора — [frontend/src/Calculator.jsx](frontend/src/Calculator.jsx). Она разбита на шаги:

1. данные питомца;
2. природные условия;
3. сценарий мемориала.

Такой порядок постепенно собирает обязательную анкету, затем параметры для подбора и только после этого уточняет место посадки. Перед отправкой frontend проверяет обязательные поля, но окончательная валидация всё равно выполняется backend: клиентскую проверку можно обойти, поэтому она используется для удобства пользователя, а не как граница доверия.

После расчёта экран показывает био-капсулу, прогноз срока и дерево. Для «Эко-парка» пользователь переходит к карте. Для «Собственного участка» создаётся посадка с `eco_zone: null` и текстом «Собственный участок», после чего открывается «Мой сад».

Регион выбирается из доступных регионов каталога зон; климат отображается как автоматически назначаемое, недоступное для ручного изменения поле. Близость к воде вводится как «Да»/«Нет» и передаётся в расчёт для последующего фильтра карты.

### 5.4. Личный кабинет

Экран [frontend/src/Profile.jsx](frontend/src/Profile.jsx) показывает профиль и карточки питомцев. Данные загружаются из профиля API и списка питомцев. PATCH-запросы изменяют только выбранную карточку/профиль, фотографии отправляются через `FormData`.

Главная страница не совмещена с личным кабинетом: дневник остаётся в «Моём саду», как было определено пользовательским требованием. Это разделение уменьшает смешение двух задач — наблюдения за посадкой и редактирования исходных персональных данных.

### 5.5. Интерактивная карта

Карта расположена в [frontend/src/MapZones.jsx](frontend/src/MapZones.jsx). Она использует `MapContainer`, `TileLayer`, `Marker` и хуки React-Leaflet. При загрузке зон карта подбирает границы по точкам, а при выборе точки перемещает viewport к ней. Список и маркеры используют одни и те же отфильтрованные данные, чтобы поиск не оставлял на карте точки, отсутствующие в списке.

Карточка выбранной зоны находится в левой панели, а не поверх карты. Высота карты ограничивается CSS, панель с описанием прокручивается; это сделано после проверки реального UX, где карта перекрывала хедер или информацию о точке.

Если расчёт связан с мемориалом, карта показывает только зоны выбранного региона и его климата; ответ «Да» о водоёме дополнительно оставляет только `near_water`-зоны. Демонстрационные точки имеют отдельную метку и предупреждение о приблизительных координатах.

Тайлы получаются с OpenStreetMap, а не хранятся в приложении. Это избавляет прототип от необходимости поставлять собственные картографические изображения и позволяет использовать масштабирование/панорамирование, но требует сети и соблюдения политики провайдера тайлов.

### 5.6. Главная страница и дневник

Экран «Мой сад» находится в [frontend/src/Dashboard.jsx](frontend/src/Dashboard.jsx). Он объединяет данные посадки, питомца, породы, зоны и care logs, затем показывает дерево и историю ухода. Добавление записи отправляет заголовок, дату, текст и необязательное фото.

Личный кабинет и журнал разделены намеренно: дневник описывает историю ухода за деревом, а профиль редактирует контактные данные и карточку питомца.

### 5.7. Стилизация и адаптивность

Общие стили находятся в [frontend/src/index.css](frontend/src/index.css). Используются CSS Grid/Flexbox, дизайн-токены в `:root`, адаптивные media queries, состояния загрузки, пустых списков, ошибок и кнопок. Для карты предусмотрены отдельные стили Leaflet и адаптивная компоновка.

## 6. Основные пользовательские сценарии

### Сценарий A: создание посадки в эко-парке

1. Пользователь входит в аккаунт.
2. Заполняет сведения питомца и загружает фотографию по желанию.
3. Вводит регион, климат, тип почвы, освещённость, предпочтения и комментарий.
4. Выбирает эко-парк как сценарий.
5. Frontend создаёт питомца и отправляет параметры в API расчёта.
6. Backend валидирует значения, вычисляет срок, подбирает дерево и сохраняет `CapsuleCalculation`.
7. Пользователь видит рекомендацию, может скачать PDF и открыть карту.
8. На карте выбирает зону и создаёт `PlantedTree`.
9. «Мой сад» загружает посадку и позволяет вести дневник ухода.

### Сценарий B: посадка на собственном участке

Первые шаги расчёта те же. В последнем шаге пользователь выбирает собственный участок. После получения рекомендации отдельное действие создаёт посадку с пустой связью `eco_zone`, но с `location_details = "Собственный участок"`. Географическая зона не выдумывается и не требуется для завершения пользовательского сценария.

### Сценарий C: редактирование карточки питомца

Пользователь открывает личный кабинет, меняет текстовые поля и/или фото. Frontend посылает PATCH только для ID карточки. Backend получает объект через queryset текущего владельца, проверяет даты и размер фото и сохраняет запись.

### Сценарий D: экспорт паспорта

На экране результата пользователь нажимает «Скачать PDF». Запрос получает серверный документ по ID сохранённого расчёта. Документ строится на основе БД, поэтому содержит сохранённые данные и не зависит от того, оставалась ли исходная форма открыта.

## 8. Структура базы данных

### 8.1. Основные сущности

| Модель | Назначение | Основные связи |
|---|---|---|
| `User` | Аккаунт и контактные данные | владеет питомцами и расчётами |
| `Pet` | Анкета и фото питомца | принадлежит `User`; связывается с `CapsuleCalculation` и посадкой |
| `TreeSpecies` | Каталог пород и критерии пригодности | может быть рекомендована расчётом и использована посадкой |
| `CapsuleCalculation` | Входные параметры и сохранённая рекомендация | связана с пользователем, питомцем и рекомендуемым деревом |
| `EcoZone` | Публичная географическая точка посадки | может быть выбрана посадкой |
| `PlantedTree` | Фактически оформленная посадка | связана с расчётом, питомцем, породой; зона необязательна |
| `TreeCareLog` | Событие дневника | принадлежит одной посадке |

### 8.2. Почему расчёт и посадка разделены

Расчёт и посадка — разные состояния процесса. Пользователь может получить рекомендацию и скачать PDF до окончательного выбора места. Поэтому `CapsuleCalculation` хранит параметры и результат, а `PlantedTree` создаётся отдельно после подтверждения места. Связь OneToOne между ними предотвращает создание нескольких посадок из одного расчёта.

### 8.3. Почему вес хранится в расчёте отдельно

У питомца вес может измениться после создания мемориала. Если бы PDF заново читал актуальный вес из карточки, старый прогноз перестал бы быть воспроизводимым. `CapsuleCalculation.weight_kg` фиксирует исходный вес, использованный формулой.

## 10. Запуск проекта для демонстрации

## 12. Ограничения текущей версии и дальнейшее развитие

Эти пункты важно озвучивать на защите как осознанные границы прототипа:

1. **Экспертная формула ориентировочная.** Коэффициенты заданы для прототипа и не прошли лабораторную валидацию. Для реального планирования нужны консультации агронома/материаловеда и проверка факторов температуры, влажности, состава материала и технологии посадки.
2. **Базовый срок для смеси фиксирован.** В текущем интерфейсе выбирается сценарий и условия, но нет выбора отдельного материала капсулы. Для другой смеси потребуется модель материала и соответствующий `Tbase`, а не переименование текущего результата.
3. **Каталог видов не содержит реальных фотографий.** Поле `image` предусмотрено, но начальная миграция добавляет характеристики пород без файлов изображений. В рекомендации используется графическая иконка.
4. **Каталог демонстрационный.** Совместимость видов заполнена начальными строками и требует проверки региональным специалистом перед практическим применением.
5. **Климатическая классификация демонстрационная.** Регион автоматически сопоставляется с одной из четырёх модельных зон; это упрощение, не детальная метеорологическая карта.
6. **Данные карты демонстрационные.** Координаты и правила зон являются начальными примерами. Признак близости к воде задан для фильтра прототипа и не заменяет географическую проверку расстояния до береговой линии. Для реального сервиса координаты, водоёмы и доступность территории нужно подтвердить у владельцев и поддерживать через административный процесс.
7. **OpenStreetMap зависит от сети.** При отсутствии интернета тайлы карты не загрузятся; это не отключает остальные API-функции.
8. **Файлы хранятся локально.** Для production нужны постоянное объектное/файловое хранилище, резервное копирование, CDN/раздача media и политика удаления.
9. **Dashboard сфокусирован на первой посадке.** Backend отдаёт список посадок, но текущий экран сводки в первую очередь выводит первую запись; интерфейс выбора нескольких садов можно развить отдельно.
10. **Production-hardening не завершён.** Перед публикацией необходимо хранить `SECRET_KEY` только в переменной окружения, отключить `DEBUG`, задать `ALLOWED_HOSTS`, включить HTTPS, ограничить CORS доверенными доменами и подготовить настройки статических и media-файлов. В текущих настройках видны параметры режима разработки, поэтому их нельзя считать готовой production-конфигурацией.
11. **Автоматические тесты проверяют функциональную логику, не полный UX.** Для завершения приёмки полезны браузерные сценарии и проверка адаптивности на целевых устройствах.

### Возможные направления развития

- хранить материалы капсул как отдельные модели с индивидуальным `Tbase`;
- согласовать коэффициенты и диапазоны с профильными специалистами;

- перейти от локального media к постоянному хранилищу;

## 13. Краткий план устной защиты

1. **Проблема и цель:** объединить память о питомце, рекомендацию дерева и последующий уход в едином цифровом сценарии.
2. **Демонстрация пользовательского потока:** вход → анкета → расчёт → PDF → карта или собственный участок → дневник.
3. **Архитектура:** React SPA, REST API Django, PostgreSQL; показать разделение ответственности.
4. **Модель данных:** показать связь Pet → Calculation → Planting → CareLog и необязательность EcoZone.
5. **Алгоритм:** записать формулу, разобрать один числовой пример и обозначить, что коэффициенты — согласованная модель прототипа.
6. **Каталог деревьев:** объяснить, что пустая БД была причиной отсутствия рекомендаций; миграция добавляет начальные виды и критерии.
7. **Надёжность:** показать проверки владельца, валидацию дат/фото и автоматизированные тесты.
8. **Ограничения и планы:** прямо обозначить отсутствие фотографий деревьев, необходимость верификации модели и production-hardening.

### Пример короткого объяснения формулы

«Срок разложения в прототипе рассчитывается как произведение базового срока и трёх поправок. Для текущей смеси базовый срок равен шести месяцам. Например, при весе 4,5 кг коэффициент веса равен 0,9, суглинок даёт 1,0, умеренный климат — 1,0. Итог — 5,4 месяца. Все множители возвращаются в API и сохраняются вместе с весом-снимком, поэтому результат можно объяснить пользователю и повторно вывести в PDF».

## 14. Возможные вопросы преподавателя

### Почему выбран PostgreSQL, а не SQLite?

Для проекта была зафиксирована одна целевая СУБД — PostgreSQL. Это исключает разные поведения между локальным fallback и рабочей базой. Настройка подключения берётся из окружения, а схема и начальные данные задаются Django migrations.

### Почему возраст не вводится вручную?

Ручное число могло противоречить датам. Поэтому возраст в полных годах рассчитывается из рождения и ухода, а backend проверяет порядок дат. Если одной из дат нет, возраст остаётся неизвестным.

### Почему деревья раньше не появлялись?

API каталога возвращал данные из таблицы `TreeSpecies`, но в локальной PostgreSQL было ноль записей. Поэтому экран корректно получал пустой массив. Добавлена миграция, которая начально заполняет каталог десятью видами.

### Как обеспечивается, что пользователь не редактирует чужие данные?

Для питомцев queryset ограничен текущим владельцем. Для посадок и care logs сериализатор проверяет принадлежность расчёта, питомца и посадки пользователю. Профиль возвращает `request.user`, а административные зоны защищены staff permission.

### Почему расчёт сохраняется отдельно от посадки?

Рекомендацию и PDF можно получить до выбора конкретной зоны. Отдельные сущности отражают этот жизненный цикл; посадка создаётся только после подтверждения места. Для собственного участка зона не нужна.

### Можно ли считать прогноз биодеградации точным научным сроком?

Нет. Это прозрачная демонстрационная экспертная формула с согласованными коэффициентами. Она полезна как объяснимая модель интерфейса, но для практических экологических утверждений её необходимо валидировать экспериментально и у профильных специалистов.

### Где фотографии пород деревьев?

Их пока нет. В миграции добавлены записи и текстовые характеристики, поле `image` допускает файл, но начальные данные изображений не загружают. В текущей рекомендации используется иконка.

## Заключение

В результате реализован функциональный прототип экологичного мемориала питомца: персональные данные сохраняются в PostgreSQL, расчёт воспроизводим, дерево подбирается из заполненного каталога, место выбирается на интерактивной карте или задаётся как собственный участок, а историю можно продолжить в дневнике и PDF-паспорте.

Ключевым инженерным результатом стало связывание интерфейса с реальными моделями и API: пустой каталог выявлялся как проблема данных, а не маскировался статическими frontend-значениями; срок и возраст объяснимы и проверяемы; пользовательские сущности защищены проверками владения. Ограничения модели и демонстрационных данных явно перечислены, что задаёт основу для дальнейшей проверки предметной области и подготовки production-развёртывания.
